大型交易所代码库的失败方式高度可预测：所有东西互相长进去，直到改
一处费率能弄坏一笔转账。ffex 的组织方式让这种失败在结构上就很难
发生：平台按业务域硬边界切分，每个域都能被单独推理、单独扩容、
单独审计。

## 业务域地图

| 业务域 | 职责 |
|---|---|
| **身份与账户** | 注册、登录、会话、权限、KYC 就绪的身份流程、邀请、安全设置 |
| **现货交易** | 现货市场的下单、计划委托、撮合、余额与持仓 |
| **衍生品交易** | 永续合约：杠杆持仓、保证金模式、批量订单、仓位管理 |
| **行情** | Ticker、深度、成交、K 线，快照 + 增量 WebSocket 推送 |
| **清算与风控** | 资金费率、强平、减仓、保险基金机制、风险监控 |
| **钱包与托管** | 充值、提现、地址管理、链上监控、冷热分离、第三方托管适配 |
| **产品线** | 期权与 OTC 是一等公民产品域，不是外挂 |
| **做市** | 机器人/做市运行器，交易对开关与库存纪律 |
| **通知** | 多渠道投递（邮件、短信、webhook 类渠道），带重试与回执 |
| **后台运营** | 管理控制台：币种、费率、风险参数、用户、财务、审计导出 |
| **平台服务** | 调度、跨域同步 worker、共享运行时 |

这张表的重点不是清单本身，而是**每一行都对其数据与不变量拥有唯一
owner**。交易主链在其中这样穿行：

> 下单入口 → 交易前校验 → 路由 → **撮合** → 执行 → 持久化 → 推送

每一个箭头要么是类型化的内部 RPC（同步校验，调用方需要立刻得到
答案），要么是异步主干上的事件（交易员不该等待的场景）。没有第三
种跳法——没有绕过域边界直连他域数据库表的路径，也没有服务去读
别的服务的表。

## 边界规则

三条规则让业务域保持诚实：

1. **每个域拥有自己的数据。** 跨域读取走契约，不走对方的存储；一个
   域需要对另一个域的状态变化做出反应时，消费事件。
2. **契约类型化且带版本。** 内部同步调用是从唯一 proto 真源生成的
   gRPC 服务；破坏性变更是新版本，不是突然袭击。
3. **触碰资金的状态变更以事件承载、可安全重放。** 账本、通知与
   分析管道消费的是有序、幂等的事件流——绝不是直插他域内部的
   回调。

## 运营方为什么该关心

业务域边界常被当作开发者的便利来推销，但对交易所而言它是风控：

- 营销通知的 bug 碰不到订单处理，因为两者之间没有代码路径。
- 行情压力不会拖慢下单，因为它们独立扩容。
- 审计人员可以只审托管域，而不必读完整平台。
- 新产品线（新衍生品类型、新交易台）以新业务域落地，而不是把改动
  洒满整个代码库。
