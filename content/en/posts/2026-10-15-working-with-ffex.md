This blog shows what the ffex platform is built to achieve. Turning that
into a running exchange is a structured engagement, and this page explains
how it works.

## What can be delivered

- **The full platform** — trading, custody, risk, back-office and frontends,
  in the Java stack, the Go stack, or both.
- **Domain modules** — for operators with an existing platform who need one
  hard problem solved properly: a matching layer, a custody and wallet
  domain, a clearing and risk engine, or the observability stack.
- **Customization and integration** — new product lines as new domains,
  third-party custody and liquidity integrations, regional compliance
  adaptations.
- **Deployment and operations support** — Kubernetes-based deployment
  blueprints, runbooks, and the release pipeline discipline described in
  [the previous article](../2026-10-14-observability-and-operations/).

## How an engagement runs

1. **Intro call** — goals, scope, constraints. Short.
2. **Technical deep-dive under NDA** — this is where the internals live:
   matching core design, capacity engineering, security architecture and
   the parts we deliberately keep off this blog.
3. **Scoped pilot** — a defined workload profile, validated against real
   numbers, on agreed infrastructure.
4. **Delivery** — staged, pipeline-gated, with acceptance criteria defined
   up front.

## What we keep off this blog, on purpose

Exchange engineering has a peculiar marketing tradition: vague
architecture diagrams and throughput claims nobody can verify. We would
rather show the reasoning — the invariants, the failure modes, the
disciplines — and reserve the implementation details for conversations
where they belong. If a vendor's public materials fully describe their
matching engine, either the engine is simple or the description is.
